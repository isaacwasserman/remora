Fix control-flow correctness for nested and condition-chain blocks, and key durable steps by path

- `switch-case` now falls back to its `default` case again. The match lookup used `findIndex(...) ?? ...`, but `findIndex` returns `-1` rather than `undefined`, so the fallback never ran and any workflow relying on a default case failed with `UNRECOGNIZED_CASE`.
- `wait-for-condition`'s condition chain is now modelled by validation: its steps are reachable (previously reported as unreachable, making the step unusable), cycles routed through it are detected, a dangling `conditionStepId` is a diagnostic instead of a crash, and `condition` is checked against the scope the chain actually produces.
- A step following a loop whose body ends in a nested block no longer crashes validation. Block steps now own their own continuation, so it stays reachable at any nesting depth and is typed with the post-block scope — loop variables no longer leak past the loop.
- `ask-supervisor` binds the answer string to `steps.<id>`, matching its declared output type (it previously bound `{ answer }`). `wait-for-condition` now declares its output as unknown rather than `null`, matching the condition value it binds.
- `ask-supervisor` no longer swallows adapter failures. Both the intervention request and the answer read return a `ServiceResult` whose error was never checked, so a failing adapter left the step polling forever for an answer to a question that may never have been asked; failures now surface as `ASK_SUPERVISOR_ERROR`.
- Delays are now durable. `DurableContext.sleep` checkpoints its wake-up deadline before waiting and serves only the time still owed, so a resumed run no longer re-serves elapsed delays: a `sleep` step interrupted near its end finishes immediately on resume instead of restarting from zero, and resuming a long `wait-for-condition` or `ask-supervisor` wait no longer replays the entire elapsed poll history. `sleep` takes a step path for this reason.
- `ExecutionState.status` gains `sleeping`, `awaiting-condition`, and `awaiting-input`, so a host can tell a run that is deliberately blocked from one that has hung, and see what it is blocked on. All three are non-terminal; consumers that only branch on `success`/`error` are unaffected, but exhaustive `switch`es over `status` will need the new arms. `ask-supervisor` reports `awaiting-input` only after the question has actually been sent. Updates from inside a `wait-for-condition` condition chain are now forwarded to the stream as they happen, instead of being swallowed at its poll-callback boundary.
- **Breaking (adapter authors):** `DurableContext.waitFor` returns an async generator rather than a promise, so callers drive it with `yield*` (or drain it) to take the settled value. `poll` may stay a plain async function — it may now also be an async generator, whose yields `waitFor` re-emits, which is how a waiting step surfaces progress from inside an attempt.
- **Breaking (adapter authors):** `now()` and `uuid()` are gone from `DurableExecutor`/`DurableContext`. They were only checkpointed when called inside a step frame and silently fell back to raw `Date.now()`/`crypto.randomUUID()` at the top level, so durability depended on incidental nesting. Produce nondeterministic values inside a `step` instead — its recorded result replays like any other. This also removes the adapter's frame stack, and makes `ask-supervisor`'s question id stable on its own rather than by virtue of an enclosing step.
- A binding introduced by only some `switch-case` branches is now typed as nullable, so reading it after the switch is reported as possibly-null instead of as definitely present. Relatedly, accessing through any nullable union is now a single warning on the union rather than a warning plus a hard error for its `null` alternative — that escalation would have made every read of a branch output fail validation. An access where *no* alternative resolves is still an error.
- An `ask-supervisor` step whose `choices` is empty while `allowFreeResponse` is false is now rejected, since the supervisor would get a question with nothing to answer and the step would wait forever. A literal empty list fails validation; a dynamic expression that resolves to empty fails at execution time with `TYPE_ERROR`, before the question is sent.
- Durable step keys are derived from a step's path (e.g. `loop.2.callApi`, `wait.attempt.1.check`) instead of a per-frame positional counter, so a key no longer depends on how much ran before it. Two sibling `wait-for-condition` steps no longer share checkpoints, and a condition chain re-runs on every poll attempt instead of replaying the first attempt's results.
